Can we animate SVGs?

Yes, but only for brand motifs. Variant A builds its hero demo both ways; flip Demo tech to compare.

  • Inline SVG with CSS keyframes gives exact vector overprint and logo-true shapes, follows the theme, and can play once and pause. Its text can’t reflow, so at phone width the notes shrink to 8–10px, and terminal output can’t live inside it. As an <img> it loses pause and the theme toggle.
  • HTML scenes on a small timeline keep real, selectable text that reflows, follow the tokens in both themes, and support chapters, pause and replay. Warp, Linear, Raycast, Bun and Ghostty rebuild their product UI the same way; none of the 13 sites inspected uses SMIL, Lottie or Rive.
  • So: HTML scenes for the CLI, addon, pull request and agent demos; animated SVG for the mark, the plates and READMEs.

Decided

  • Landing: hero A; problem, demo and commands D; features A; agent D; FAQ and last call A. Built as variant F with half the text.
  • Header: reveal. Only the logo while the hero is on screen; a compact bar with section links and Get started slides in once the hero’s install command scrolls past. Now F’s default, and the design system’s SiteHeader (F renders it from the system’s classes). The other four stay on the Header switch for reference.
  • Docs: Illustrated (3), with inline figures and the clerk TOC.
  • Design system: the accent button is a deeper magenta (#d9006c, hover #c7005f) with a white label. White on the plate magenta is 3.5:1, so the fill had to deepen to pass 4.5:1.

Open questions

  1. Motion. The demos play once when first seen, which the design system’s “nothing animates on its own” rule forbids today. Amend the rule to allow one play on first view (never looping, always pausable, end state under reduced motion), or ship every demo as click to play? The bar’s Motion button shows all three behaviours.
  2. Words. The CLI prints differs; the design system’s badge says changed. Which one does the site use?
  3. Design-system gaps the prototypes ran into, to add as tokens before the build: a container width (1200px), a hero size above display and phone sizes for headings, the docs layout widths (sidebar 268px, TOC 268–304px, article 760–900px), a dialog scrim and a selected-item tint. Also: the SiteHeader doesn’t fit four nav links and the search field between 768 and about 1120px; the prototypes collapse it in two steps.
  4. Docs layout. Classic, Notebook or Spacious? Spacious exists only in the Base UI build of Fumadocs and is a client component. And is Fumadocs’ primary colour cyan (links, active items) or ink?
  5. Hosting. Static export or a server build? It decides how search and the per-page Markdown routes for agents work.
  6. Demo numbers. Pixel counts and timings in the demos are illustrative and labelled so. The research recommends generating each scene from real CLI output in CI, so the page can’t drift from the product.
