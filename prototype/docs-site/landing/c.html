$ pnpm visual:update

            

              
Write the baselines

              
Snapshots every story and writes the PNGs to .visual-check/baselines/ beside each Storybook. You commit them, and they're reviewed in the pull request like code. Only a person runs it: with CI set, update exits 2.

            

          

          

            
$ pnpm visual:check

            

              
Check every story

              
Snapshots the stories and compares each with its baseline. It exits 0 when they match; 1 for a visual diff, a broken story, a missing baseline or an orphan; 2 for a tool or config problem.

            

          

        

        
Flags you'll reach for:--affected--filter <regex>--storybook <name>--shard 2/3--reporter json

landing--features✓passed

      

        

          

            
A baseline from your Mac passes in CI

            
The browser runs in visual-check's own image, pinned by digest, as linux/amd64 by default. A baseline written on a Mac passes in Linux CI and on Windows. That's why the snapshots don't turn flaky between machines.

            
On an M-series Mac, linux/amd64 runs emulated, so it's slower. linux/arm64 is faster, and the default tolerance absorbs the small difference.

Only the stories a change can reach

            
With --affected, it snapshots only the stories your changed files reach. It drives the browser itself, with no Playwright, and shards across runners with a consistency check.

            

              
3.30/s
captures, against 2.71 for Playwright's run-server: 2 workers on 2 vCPUs, 300 real stories.

              
80 ms
until a story is ready, instead of 170 ms, through Storybook's test path.

            

          

          

            
Honest with real stories

            
Animations are captured at their end state. It waits for fonts and images, and a wait hook covers the rest. Masks hide what changes on every load. A flaky snapshot is retried, listed and never fails the run.

            

              

                
card.stories.tsx

                
export const Default = {
  parameters: {
    ...visualCheck({
      modes: ['dark', 'mobile'],
      masks: { clock: { selector: '[data-clock]' } },
      wait: async ({ canvas }) => {
        await canvas.findByText('Late content')
      },
    }),
  },
}

Your agent can't see what it changed

            
init writes an agent skill: a Markdown file and a small Node script. Your agent runs it after UI changes, before it says the work is done, and reports which stories moved, by how many pixels, with the paths to the visual diffs.

            
    
              
  • It never accepts its own changes. No update, no raised tolerance and no disabled story without your OK.
    • 
              
  • It never opens a snapshot or a visual diff. It gives you their paths.
    • 
              
  • It proposes each fix with its snippet, and applies it once you agree.
    • 
              
  • It's a CLI and a skill file, so there's no MCP server to run.
    • 
            

          

        

      

    

  


  
  

    

      
landing--faq✓passed

      

        

          

            
Before you run init

            
Coming from Loki, Lost Pixel or the Storybook test-runner? Run init beside it; the docs have a page for moving over.

            
Moving over to visual-check

          

          

            
Do I need Docker?
By default, yes: that's how the pixels match everywhere. Without Docker, platform: 'host' uses a local browser, and baselines then only match on the same OS.

            
I'm on Apple silicon. Is it slow?
It runs linux/amd64 through Rosetta by default, emulated, so it's slower than native. platform: 'linux/arm64' is faster, and the default tolerance absorbs the small rendering difference.

            
Will it be flaky?
Animations are captured at their end state, and readiness waits for fonts and images. A failing snapshot is retried once, and a flaky one is listed but never fails the run.

            
Where do baselines live, and who writes them?
In .visual-check/baselines/ beside each Storybook, committed with your code. Only a person running update writes them. CI never does: update with CI set exits 2.

            
How is it different from a hosted visual-testing service?
It runs in your CI and on your machine. There's no per-snapshot pricing, no upload and no hosted review: you review in the pull request, the Storybook addon and the report.

            
Which Storybooks and CIs does it support?
Storybook 9.1, 10 and 11; the addon needs 10. GitHub Actions has an Action and a reusable workflow, and the CLI runs anywhere Docker does.

            
What does it change in my repo?
visual-check.config.ts, .storybook/visual-check.ts for modes, two npm scripts, the agent skill and .visual-check/ folders. It never edits your preview or your stories.

            
Which frameworks and package managers?
React, Vue, Svelte, Solid and vanilla run in the test apps. It needs Node 22.17 or later, with npm, pnpm, Yarn or Bun.

            
What does it cost?
Nothing. It's open source under the MIT licence.
