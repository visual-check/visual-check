Agents change UI faster than anyone looks at it Every check passed, and the pricing page moved A one-line change moves forty stories Nobody reads pixels in review

A coding agent reads code and runs what you give it: the type checker, the linter, the unit tests. On a padding change they all pass, because none of them looks at the screen. The agent can't see what it changed, and nobody opens every story it touched.

A shared token or component sits under dozens of stories. Change it and every one of them can move, while the pull request shows one line of CSS. Nobody reads pixels in review, so the change ships as it is.

visual-check gives that change something to be checked against: every story it can reach, compared with the baseline you approved, with the moved ones named.

The Claude Code docs put it plainly: “Give Claude something it can run that comes back pass or fail.” visual-check exits 0 when every story matches, 1 when a story differs, broke or has no baseline, and 2 when it couldn't run. Read the guide

In CI the same exit codes fail the job: 0 when every story matches, 1 when a story differs, broke or has no baseline, and 2 when visual-check couldn't run.

What the skill tells your agent A skill with four rules and one script Your coding agent can run the same check

init writes the skill into your repo: a Markdown file, a script with no dependencies and a small setup file. Your agent runs the same CLI you do, reads the JSON report and answers in a fixed shape.

If you work with a coding agent, init also writes a skill that tells it to run visual-check after UI changes and report what moved. It never accepts a change for you.

  • Run it after UI changes, before saying it's done

    “Use after changing UI code, styles or stories, before saying the work is done, and whenever asked whether a change alters how stories look.”
    The skill's description, which is how the agent knows when to load it

  • Report paths, never open images

    “Never open a snapshot, a baseline or a visual diff. Give their paths instead.”

    You get the counts, then each story that differs or broke with its mode, its pixel count and its diff path. Missing baselines, orphans, flaky snapshots and a reused Storybook are reported too.

  • Never make a failure pass on its own

    “Never raise tolerance, disable a story or run update to make a failure pass without the user's explicit OK.”

    The agent runs test. Accepting a change is update, and that stays your call.

  • Propose fixes, apply them when you agree

    “Propose each fix with its snippet, and apply it only once the user agrees.”

    Fixes come in a set order: a run error first, then broken stories by reason, then remote content, then flaky snapshots with a mask or a wait.

Why a skill and not a server

A skill is a text file and a plain Node script. The agent calls the CLI you already have and loads no tool schemas, so there's nothing to host and nothing extra in its context.

One command sets up you and your agent Three commands, and one of them is yours alone One command to try it Three commands, one config file

npx @visual-check/cli init finds your Storybooks, asks a few questions, installs what it needs and writes one config file. A first update then test passes without editing a story.

What it changes in your repo

  • visual-check.config.tsThe one config file: your Storybooks and their URLs.
  • .storybook/visual-check.tsModes and options for every story, through the visualCheck(...) helper.
  • visual:check and visual:updateTwo scripts in package.json.
  • .agents/skills/visual-check/The agent skill, linked from .claude/skills/visual-check. Answer No and it's left out.
  • .visual-check/Baselines beside each Storybook, committed. The report stays out of git.

It never edits your preview file or your stories.

The same check, wherever you review

The agent is one way to run it. Your terminal, the GitHub Action and the Storybook addon run the same check against the same baselines.

Same pixels on every machine

The browser runs in visual-check's own image, pinned by digest, as linux/amd64 by default. A baseline written on a Mac passes in Linux CI and on Windows, because each one renders in the same browser with the same fonts.

On an M-series Mac the amd64 image runs emulated, so it's slower. platform: 'linux/arm64' is the faster option, and the default tolerance absorbs the small rendering difference.

Fast because it's narrow

  • Affected stories. A run covers only the stories your changed files can reach; --all covers every one.
  • Its own browser driver, no Playwright. 3.30 captures/s against 2.71 for Playwright's run-server, 2 workers on 2 vCPUs over 300 real stories.
  • A story ready in 80 ms instead of 170 ms, through Storybook's test path.
  • Identical bytes pass without decoding images, 98–99% of the time on unchanged snapshots.
  • Shards split a run across CI jobs, with a consistency check for missing baselines and orphans.

Nothing leaves your machine

  • No service and no account, and no per-snapshot bill.
  • Baselines are PNG files in your repo, reviewed in the pull request like code.
  • MIT licence.

Honest with real stories

  • Animations are captured at their end state.
  • Readiness waits for fonts and images, and a wait hook covers the rest.
  • Masks hide a clock by selector, or remote content by host.
  • A failing snapshot is retried once. A flaky one is listed and never fails the run.
  • The default tolerance { color: 0.01, pixels: 20 } still catches 89–100% of small deliberate changes in the measured set. Counting anti-aliased pixels caught 259 of 260 hidden icons, against 118 when they're ignored.

  parameters: {
    ...visualCheck({

        await canvas.findByText('Late content')

Questions before you run it

Something missing? Open an issue on GitHub.

Does the agent approve its own changes?

No. The skill runs test and reports. It tells the agent never to raise tolerance, disable a story or run update to make a failure pass without your OK. Baselines change only through update, run by you or at your request, and never in CI: update with CI set exits 2.

Which coding agents can use the skill?

init writes it to .agents/skills/visual-check/ and commits a link at .claude/skills/visual-check, so Claude Code and agents that read Agent Skills pick it up. Answer No to Install the agent skill? and init leaves it out.

Does the agent look at the images?

No. It gives you each story, mode, pixel count and diff path instead of opening a snapshot, a baseline or a visual diff. You open the visual diff in .visual-check/report/, in the Storybook addon, or see the changed baselines in the pull request.

Do I need Docker?

By default, yes: that's how the pixels match everywhere. Without Docker, platform: 'host' uses a local browser, and baselines then only match on the same OS.

I'm on Apple silicon. Is the amd64 default slow?

It runs linux/amd64 through Rosetta by default, emulated, so slower than native. platform: 'linux/arm64' is faster, and the default tolerance absorbs the small rendering difference.

Will it be flaky?

Animations are captured at their end state, readiness waits for fonts and images, a failing snapshot is retried once, and a flaky one is listed but never fails the run.

Where do baselines live, and who writes them?

In .visual-check/baselines/ beside each Storybook, committed. Only update writes them, run by you or by your agent when you ask. CI never does: update with CI set exits 2.

How is it different from a hosted visual-testing service?

It runs in your CI and on your machine. There's no per-snapshot pricing, no upload and no hosted review: you review in the pull request, the Storybook addon and the report.

Which Storybooks and CIs does it support?

Storybook 9.1, 10 and 11; the addon needs 10. GitHub Actions has an Action and a reusable workflow, and the CLI runs anywhere Docker does. Node 22.17 or later, with npm, pnpm, Yarn or Bun.

What does it change in my repo?

visual-check.config.ts, .storybook/visual-check.ts for modes, two npm scripts, the agent skill and .visual-check/ folders. It never edits your preview or your stories.

What does it cost?

Nothing. It's MIT licensed.

Coming from Loki, Lost Pixel or the Storybook test-runner?

Run init beside it. The docs have a page for moving over.
