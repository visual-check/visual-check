See exactly what moved Drag to see what your change did Same pixels on your laptop and in CI

Code review shows what changed in the code. visual-check shows what changed on screen: every story compared with the baseline you approved, with a pixel count and a visual diff. Drag the line across the card. Its button gained 12px of padding on each side and its border went from 1px to 2px. visual-check counted 1288 pixels that differ. The browser runs in visual-check's own Docker image, pinned by digest. A baseline written on a Mac passes in Linux CI and on Windows, so a story fails only when it really moved.

Run in your repo
$ npx @visual-check/cli init

Also pnpm dlx, yarn dlx or bunx. Storybook 9.1, 10 and 11. MIT licence.

Review reads the code, not the pixels A one-line change, two stories moved

A one-line change to a shared token or component can move forty stories. The pull request shows one line, so one line is what gets reviewed. Coding agents add to it: they make more UI changes, in larger diffs, and can't see what they changed.

Three commands and one config file

        
init sets it up. update writes baselines, on your machine. test compares, wherever it runs.

      

      

        

          

            
visual-check init

            

              Set up visual-check in this project
              
Finds each Storybook with its start script and port, and checks for Docker. It asks a few questions, installs the packages and writes .storybook/visual-check.ts, two npm scripts and the agent skill. It never edits your preview or your stories.

            

          

          

            
visual-check update

            

              Write missing and failing baselines and delete orphans (local only)
              
A person runs it when the change is the one they meant. The new PNGs go into the pull request beside the code. With CI set, it exits 2.

            

          

          

            
visual-check test

            

              Capture snapshots and compare them with baselines
              
Exits 0 when every story matches, 1 when one differs, is broken, missing or an orphan, and 2 when the tool or its setup fails. The same command runs in your terminal, in CI and for your agent.

              
--affected--all--filter <regex>--base <ref>--storybook <name>--shard <k>/<n>--reporter live|log|json

"scripts": {

The Action needs only contents: read, so it works on pull requests from forks. For shards, call visual-check/action/.github/workflows/test.yml@v1 with shards: 4.

        

      

    

  


  
  

    

      

        
What it does, with the numbers

        
A spec sheet rather than a list of promises. The figures come from public CI runs of the test apps and from the project's own benchmarks, and each one says where it was measured.

      

      

        

          
            
Rendering

            
BrowserChromium 157, inside visual-check's own Docker image, pinned by digest.

            
Platformlinux/amd64 by default, so a baseline written on a Mac passes in Linux CI and on Windows. linux/arm64 and host when you ask.On M-series Macs the amd64 image runs emulated, so slower. arm64 is faster, and the default tolerance absorbs the difference.

            
Windows108 passed · 16.9sDocker Desktop, the same 108 snapshots as Linux CI.

          
          
            
Comparison

            
Tolerance{ color: 0.01, pixels: 20 } by default. It still catches 89–100% of small deliberate changes in the measured set.

            
Anti-aliasingCounted, not ignored: 259 of 260 hidden icons caught, against 118 when anti-aliased pixels are ignored.

            
Unchanged snapshotsIdentical bytes pass without decoding the images, 98–99% of the time.

            
Visual diffPixels that differ in magenta; a change of size padded in cyan. Every failure names its diff file.

          
          
            
Speed

            
One run108 passed · 10.8sA GitHub-hosted runner, 4 workers, the sb11 test app.

            
Five Storybooks110 passed · 19.1sReact, vanilla, Vue, Solid and Svelte in one repo, one run.

            
Capture rate3.30 captures/s against 2.71 for Playwright's run-server, 18–24% faster.2 workers on 2 vCPUs, 300 real stories. Its own browser driver, no Playwright.

            
Story ready80 ms instead of 170 ms, through Storybook's test path.

            
SelectionOnly the stories a change can reach (affected stories). --shard k/n splits a run, and a consistency check makes sure no baseline is missing or orphaned.

          
          
            
Real stories

            
AnimationsCaptured at their end state.

            
ReadinessEach capture waits for fonts and images. A wait hook covers the rest.

            
MasksBy selector, such as a clock, or by host, such as a CDN.

            
Flaky snapshotsA failing snapshot is retried once. A flaky one is listed and never fails the run.

            
ModesA dark theme, a phone viewport, any globals you define. Each mode a story lists adds one snapshot.

          
          
            
Fits in

            
Storybook9.1, 10 and 11. The addon needs 10.

            
FrameworksReact, Vue, Svelte, Solid and vanilla in the test apps.

            
ToolingNode 22.17 or later, with npm, pnpm, Yarn or Bun. GitHub Actions has an Action; the CLI runs anywhere Docker does.

            
LicenceMIT. There's no service and no account.

import { visualCheck } from '../.storybook/visual-check'

export const Default = {
  parameters: {
    ...visualCheck({
      modes: ['dark', 'mobile'],
      masks: {
        clock: { selector: '[data-clock]' },
        cdn: { host: 'images.example.com' },
      },
      wait: async ({ canvas }) => {
        await canvas.findByText('Late content')
      },
    }),
  },
}

          

          
One story, three snapshots: the default capture, dark and mobile. The clock is masked, the CDN's images too, and the capture waits for late content.

            Give your agent a check it can run
          

          
init writes an agent skill: a Markdown file and a Node script. Your agent runs it after UI changes, before it says the work is done, and reports which stories moved, by how many pixels, with the diff paths. A CLI and a skill, not an MCP server.

    • 
              
  • Never open a snapshot, a baseline or a visual diff. Give their paths instead.
    • 
              
  • Never apply a fix before you agree. Propose each one with its snippet first.

Questions before you try it

          
The short answers. The docs have the long ones.

        

        

          
Do I need Docker?
By default, yes. That's how the pixels match on every machine: the browser runs in visual-check's own image. Without Docker, platform: 'host' uses a local browser, and baselines then match only on the same OS.

          
I'm on Apple silicon. Is the default slow?
The default image is linux/amd64, so on an M-series Mac it runs emulated through Rosetta, slower than native. platform: 'linux/arm64' is the faster option, and the default tolerance absorbs the small rendering difference.

          
Will it be flaky?
Animations are captured at their end state, and each capture waits for fonts and images. A failing snapshot is retried once, and a flaky one is listed but never fails the run.

          
Where do baselines live, and who writes them?
In .visual-check/baselines/ beside each Storybook, committed with your code. Only a person running update writes them. CI never does: update with CI set exits 2.

          
How is it different from a hosted visual-testing service?
It runs in your CI and on your machine. There's no per-snapshot pricing, no upload and no hosted review. You review in the pull request, the Storybook addon and the report.

          
Which Storybooks and CI services does it support?
Storybook 9.1, 10 and 11; the addon needs 10. GitHub Actions has an Action and a reusable workflow, and the CLI runs anywhere Docker does.

          
What does it change in my repo?
visual-check.config.ts, .storybook/visual-check.ts for modes, two npm scripts, the agent skill and .visual-check/ folders. It never edits your preview or your stories.

          
What does it cost?
Nothing. It's MIT-licensed and there's no service behind it.

          
Coming from Loki, Lost Pixel or the Storybook test-runner?
Run init beside it. The docs have a page on moving over.

          
Does my coding agent approve its own changes?
No. The skill runs test and reports. Running update, raising tolerance or disabling a story needs your OK.
