One session, start to finish

Set it up, write the baselines, change one line of CSS, see what it moved, then approve it. The terminal follows the text.

  1. Set it up once

    init finds the Storybook in apps/web, asks three questions and installs what it needs. It writes its config, two npm scripts and the agent skill. It doesn't touch your stories or your preview file.

  2. Approve what's there today

    update snapshots all 108 stories and modes and writes each one as a PNG baseline beside the Storybook. You commit them with your code. Only a person runs update. With CI set, it exits 2.

  3. Change one line

    The button gets 2px more padding. Review shows one line of CSS. It doesn't show that the modal on mobile moved too, because nobody opened it.

  4. See what moved

    test snapshots every story in the same pinned browser and compares each with its baseline. Two differ. It names them, counts the pixels, writes a visual diff for each and exits 1, so the CI check fails.

  5. Approve it, or fix it

    If the change is intended, a person runs update. The two new baselines land in the same commit as the CSS, so the reviewer sees the code and the pixels together.

The details that keep a run honest

Each claim comes with its number and where the number came from: visual-check's public CI, or the measurements in its design research.

  • Same pixels on every machine

    The browser runs in visual-check's own image, pinned by digest, as linux/amd64 by default. A baseline written on a Mac passes in Linux CI and on Windows. Pixels that differ between machines are what make other screenshot tests flaky.

Your agent can't see the UI

init writes an agent skill: a Markdown file and a small Node script. Your agent runs it after UI changes, before it says the work is done, and tells you which stories moved, by how many pixels, with the paths of the visual diffs.

It never approves its own change.Without your OK it doesn't run update, raise the tolerance or disable a story to make a failure pass. A person writes the baselines.

Before you run it

The questions people ask before init. Anything else is in the docs.

Do I need Docker?
By default, yes. The browser runs in visual-check's own image, which is how the pixels match on every machine. Without Docker, platform: 'host' uses a local browser, and baselines then only match on the same OS.
Is it slow on my M-series Mac?
The default linux/amd64 image runs emulated through Rosetta, so it's slower than native. platform: 'linux/arm64' is faster, and the default tolerance absorbs the small rendering difference.
Will it be flaky?
Animations are captured at their end state and each capture waits for fonts and images. A failing snapshot is retried once. A flaky one is listed in the output and never fails the run.
Where do baselines live, and who writes them?
In .visual-check/baselines/ beside each Storybook, committed. Only a person running update writes them. CI never does: update with CI set exits 2.
How is it different from a hosted visual-testing service?
It runs in your CI and on your machine. There's no per-snapshot pricing, no upload and no hosted review. You review in the pull request, the Storybook addon and the report.
Which Storybooks and CIs does it support?
Storybook 9.1, 10 and 11. The addon needs Storybook 10. GitHub Actions has an Action and a reusable workflow, and the CLI runs anywhere Docker does. Node 22.17 or later, with npm, pnpm, Yarn or Bun.
What does it change in my repo?
Its config (visual-check.config.ts and .storybook/visual-check.ts), two npm scripts, the agent skill and .visual-check/ folders. It never edits your preview file or your stories.
What does it cost?
Nothing. It's MIT-licensed and runs on the CI minutes you already have.
Coming from Loki, Lost Pixel or the Storybook test-runner?
Run init beside it. The docs have a page for moving over.
Can my agent approve its own changes?
No. The skill runs test and reports. It tells the agent never to run update, raise the tolerance or disable a story without your OK.
