visual-check · proof · sheet 1 of 8

Proof every story before it ships. Approve how it looks once. Know when it changes. Same pixels on your laptop and in CI.

visual-check is an open-source CLI for Storybook. It snapshots every story, compares each with the baseline you approved, and shows which stories moved, by how many pixels, in a visual diff. You approve a baseline for each story once, and it lives in your repo as a PNG file. On every change, visual-check snapshots the stories again and names each one that moved, by how many pixels, with a visual diff. visual-check runs your stories in a browser pinned inside its own Docker image. A baseline written on a Mac passes in Linux CI and on Windows, and every story that moved shows up with a visual diff.

Run in your repo
$ npx @visual-check/cli init

It finds your Storybooks, asks a few questions and installs what it needs. Also pnpm dlx, yarn dlx and bunx. MIT licence, no account.

sheet 2 of 8 · the problemplates C M

A one-line change moves forty stories.

A shared token or component sits under dozens of stories. Change one line and every story that uses it can shift. Code review shows the line. Nobody reads the pixels it moved.

Code review shows what changed in the code. visual-check shows what changed on screen.

Why the usual fixes hurt

Per-snapshot bills
Hosted services charge for every snapshot, multiplied by browsers and modes, and keep your images on their servers.
Pixels that change with the machine
Image tests written on a Mac fail in Linux CI, because fonts and anti-aliasing render differently there.
Harnesses nobody wants to own
Hand-built harnesses grow to 2,000 lines per project. The open-source tool many teams used is no longer maintained.
Agents that can't see
A coding agent makes more UI changes, in larger diffs, and can't see what any of them did to the screen.

sheet 5 of 8 · specificationthree impressions, one plate

Same pixels on every machine.

The browser runs inside visual-check's own image, pinned by digest, as linux/amd64 by default. A baseline written on a Mac passes in Linux CI and on Windows. Other image tests skip this step, and it's why they turn flaky.

i

On Apple siliconThe default linux/amd64 image runs emulated on an M-series Mac, so it's slower than native. platform: 'linux/arm64' is faster, and the default tolerance absorbs the small rendering difference.

3.30/scaptures, against 2.71 for Playwright's run-server. 2 workers on 2 vCPUs, 300 real stories.

80 msto a ready story instead of 170 ms, through Storybook's test path.

Fast because it's narrow

With --affected, it captures only the stories your change can reach. Its own browser driver talks to Chromium without Playwright. --shard splits a run across jobs, and a consistency check makes sure no baseline goes missing between them.

1 retryfor a failing snapshot. If it passes the second time, it's listed as flaky and the run still passes.

Honest with real stories

Animations are captured at their end state. Capture waits for fonts and images, a wait hook covers the rest, and masks hide what you can't control, by selector or by host.

card.stories.tsx
export const Default: StoryObj<typeof meta> = {
  parameters: {
    ...visualCheck({
      modes: ['dark', 'mobile'],
      masks: {
        clock: { selector: '[data-clock]' },
        cdn: { host: 'images.example.com' },
      },
      wait: async ({ canvas }) => {
        await canvas.findByText('Late content')
      },
    }),
  },
}

89–100%of small deliberate changes caught at the default tolerance, in the measured set.

259 of 260hidden icons caught by counting anti-aliased pixels, against 118 when they're ignored.

98–99%of unchanged snapshots pass on identical bytes, without decoding an image.

A tolerance that still sees

The default, { color: 0.01, pixels: 20 }, lets rendering noise through and stops real changes. Pixels count in CSS pixels, so 20 allows 80 at scale 2. Set it per story when you need to.

There's no service to sign up for and no per-snapshot bill. Baselines are PNG files in your repo, reviewed in the pull request like code. The report is JSON on disk.

Your agent can't see what it changed.

sheet 7 of 8 · queriesanswered before press

Questions before you run init

The ones people ask first. The docs cover the rest, with a page for each.

Do I need Docker?
By default, yes: that's how the pixels match everywhere. Without Docker, platform: 'host' uses a local browser, and baselines then only match on the same OS.
I'm on an M-series Mac. Is the default slow?
The default linux/amd64 image runs emulated through Rosetta, so it's slower than native. platform: 'linux/arm64' is faster, and the default tolerance absorbs the small rendering difference.
Will it be flaky?
Animations are captured at their end state and capture waits for fonts and images. A failing snapshot is retried once. A flaky one is listed, and never fails the run.
Where do baselines live, and who writes them?
In .visual-check/baselines/ beside each Storybook, committed. Only a person running update writes them. CI never does: update with CI set exits 2.
How is it different from a hosted visual testing service?
It runs in your CI and on your machine. Nothing is uploaded and nothing is billed per snapshot. You review in the pull request, the Storybook addon and the report.
Which Storybooks and CIs does it support?
Storybook 9.1, 10 and 11, and the addon on Storybook 10. GitHub Actions has an Action and a reusable workflow. The CLI runs anywhere Docker does.
What does it change in my repo?
A config file, the .storybook/visual-check.ts helper, two npm scripts, the agent skill and .visual-check/ folders. It never edits your preview or your stories.
What does it cost?
Nothing. It's MIT-licensed and runs on machines you already have.
Coming from Loki, Lost Pixel or the Storybook test-runner?
Run init beside it. The docs have a page for moving over.
Does my agent ever approve a change?
No. The skill runs test and reports. Running update stays your call.
