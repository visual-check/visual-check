Proof every story before it ships. Approve how it looks once. Know when it changes. Same pixels on your laptop and in CI. See the UI changes code review misses.

visual-check is a free, open-source library for visual regression testing of Storybook, under the MIT licence.

A one-line change to a shared component can move dozens of stories, and code review shows only the code. visual-check snapshots every story and shows exactly what moved. Code review shows the code, not the pixels. You approve each story's baseline once, and visual-check shows every story a change moves, with a visual diff. Other screenshot tests flake, because laptops and CI render fonts differently. visual-check snapshots every story in a pinned browser, so a story fails only when it moved. A one-line change to a shared token can move dozens of stories. visual-check snapshots every story, compares it with the baseline you approved and shows exactly what moved.

Three commands and one config file

      

      

        

          

            
visual-check init

            

              Set up visual-check in this project
              
Finds your Storybooks and writes the config, two npm scripts and the agent skill. It never edits your stories.

            

          

          

            
visual-check update

            

              Write missing and failing baselines and delete orphans (local only)
              
You run it when a change is intended. With CI set, it exits 2.

            

          

          

            
visual-check test

            

              Capture snapshots and compare them with baselines
              
Exits 0 when every story matches, 1 when one doesn't, and 2 when setup fails.

              
--affected--all--filter <regex>--base <ref>--storybook <name>--shard <k>/<n>--reporter live|log|json

Same pixels on every machine.

          
The browser runs in visual-check's own Docker image, pinned by digest. A baseline written on a Mac passes in Linux CI and on Windows.

        

        
      


      

        

          

            
3.30/scaptures with its own browser driver, against 2.71 for Playwright's run-server. 2 workers on 2 vCPUs, 300 real stories.

            
80 msto a ready story, instead of 170 ms.

          

          

            
Fast because it's narrow

            
--affected captures only the stories a change can reach, and --shard splits a run across jobs.

          

        


        

          

            
1 retryfor a failing snapshot. A flaky one never fails the run.

          

          

            
Honest with real stories

            
Captures wait for fonts and images, and masks hide what you can't control.

            

              
card.stories.tsx


export const Default: StoryObj<typeof meta> = {
  parameters: {
    ...visualCheck({
      modes: ['dark', 'mobile'],
      masks: {
        clock: { selector: '[data-clock]' },
        cdn: { host: 'images.example.com' },
      },
      wait: async ({ canvas }) => {
        await canvas.findByText('Late content')
      },
    }),
  },
}

The agent reads counts and diff paths from --reporter json, not pictures.

        

        

          
Your agent can't see the UI it changes

          
init writes an agent skill. Your agent runs it before it calls a UI change done, and reports which stories moved.

          

            
The skill's rules

            
    
              
  • Never raise tolerance, disable a story or run update without your OK.
    • 
              
  • Never open a snapshot or a visual diff. Give their paths instead.
    • 
              
  • Never apply a fix before you agree.
    • 
            

          

          
A person approves baselines. The agent never does.

        

      

    

  


  
  

    

      
      

        
Questions before you run init

      

      

        
Do I need Docker?
By default, yes: that's how the pixels match everywhere. platform: 'host' uses a local browser instead, matching only on the same OS.

        
Is the default slow on an M-series Mac?
The default linux/amd64 image runs emulated, so it's slower. platform: 'linux/arm64' is faster, and the default tolerance absorbs the difference.

        
Will it be flaky?
Animations are captured at their end state, and capture waits for fonts and images. A flaky snapshot never fails the run.

        
Who writes the baselines?
Only a person, with update. With CI set, update exits 2.

        
Which Storybooks and CIs?
Storybook 9.1, 10 and 11, and the addon on 10. GitHub Actions has an Action, and the CLI runs anywhere Docker does.

        
Coming from Loki, Lost Pixel or the Storybook test-runner?
Run init beside it. The docs have a page for moving over.
