    Readiness never waits for the network

    visual-check captures a story once Storybook says it has finished, its images have decoded and its fonts have loaded. It doesn't wait for requests that come later. So if a story fails on your first test, the story needs tuning: a wait hook for content that arrives late, a mask for content that changes, or a look at its animations.

    Before you start

    Node
    22.17.0 or later
    Storybook
    9.1, 10 or 11, with .storybook/main.* committed to git
    Docker
    Installed and running. The browser runs in visual-check's own container, so every machine renders the same pixels.
    Packages
    npm, pnpm, Yarn 1 or Yarn 4.17.1 and later. Bun works too.

    Set up

    Four steps. Run every command at the root of your repo.

    Run init

    init finds every Storybook, asks a few questions with a default for each, installs visual-check's packages and writes the setup. There's no separate install.

    init --yes takes every default. Each question shows its default after ›, and an answered question collapses to one line:

    ✓✓ visual-check init · v0.1.0
━━━━━━━━━━────────── Step 3 of 6
✓ Name of the Storybook in apps/web web
? URL of web
  Where visual-check opens it, locally and in CI. Use 127.0.0.1, not localhost.
› http://127.0.0.1:6006

    Write the first baselines

    Start Storybook and keep it running: visual-check connects to a running Storybook and never starts or builds one. Then, in a second terminal:

    update captures every story and writes its baseline to .visual-check/baselines/, next to the Storybook. Before it writes one, it loads the story a second time and captures the page again a second later, so each missing baseline takes about a second.

    visual-check 0.1.0 · update · 108 snapshots · 4 workers
108 written
written .visual-check/baselines/components-alert--info.png
written .visual-check/baselines/components-button--default.png
…

    If it ends with a warning about remote content, read Remote content before you commit. Those stories show images from another server, and a CDN can serve different bytes to different machines.

    Check the stories

    test captures each story again and compares the snapshot with its baseline. Straight after update, every snapshot should pass.

    visual-check 0.1.0 · test · 108 snapshots · 4 workers
108 passed · 10.8s
Report: .visual-check/report/report.json

    On your machine, test checks only the affected stories: the ones your changed files reach. --all checks every story. In CI it checks every story unless you pass --affected.

    Commit the baselines

    Commit the changes, baselines included. CI compares against the committed baselines and never writes its own: only update, run by a person, writes them.

    $ git add .
$ git commit -m "Set up visual-check"

    Yarn 4 on a release day

    Yarn 4 refuses a package version published less than a day ago, so yarn dlx @visual-check/cli init can fail on the day of a release. Wait a day, or list @visual-check/* under npmPreapprovedPackages in .yarnrc.yml.

    When init finishes

    It prints the next steps, with the commands for your package manager. They're the steps above:

    In a monorepo, run them from the workspace root. When init runs inside a package, the heading names the root's folder, as in Next, from acme-monorepo, and a line names the packages whose own scripts check only their Storybook.

    If the first test fails

    A snapshot that differs straight after update comes from a story that doesn't render the same way twice. visual-check doesn't wait for it, so the story needs one of three fixes:

    What you see in the visual diffFix
    Content that arrives late: data, an icon set, a chartA wait hook that waits for it
    Content that changes by itself: a clock, a random avatar, an image from a CDNA mask, by selector or by host. See Remote content
    Motion visual-check can't finish: a canvas, Lottie, a GIF backgroundA mask or a wait hook. See Animations

    A line that starts with ! is a broken story, and it names the reason: see Stories that break. Exit code 2 is a problem with the setup, not a story. For example:

    Storybook web doesn't answer at http://127.0.0.1:6006/index.json. Start it, or set its URL in the config or with --url.

    Don't raise tolerance to make a first run pass. It hides the real changes you want test to catch.

    Two questions

    A snapshot passes when it differs from its baseline by no more than the story's tolerance. Tolerance answers two questions, one key each:

    KeyQuestionDefault
    colorDid this pixel change?0.01
    pixelsHow many changed pixels are allowed?20

    Every snapshot goes through the same steps:

    1. If its bytes equal the baseline's, it passes at once, with no decoding. On unchanged snapshots that happens 98–99% of the time.
    2. If its width or height differs, it fails, whatever the tolerance.
    3. Each pixel counts as changed when its colour moved further than color.
    4. It passes when no more pixels changed than pixels allows.

    A worked example

    Take a snapshot ten pixels wide, cut across the edge of a letter, compared with pixels: 3. Each pixel is a grey, so one number from 0 (black) to 255 (white) gives its colour. The letter changed, a border and a fill got slightly darker, and two pixels carry render noise.

    PixelWhat it isBaselineSnapshotMovedcolor: 00.010.1
    Changed pixels, against pixels: 36, fails4, fails2, passes
    • At color: 0, the two noise pixels count. Render noise is never zero, so pixels would have to grow to absorb it.
    • At color: 0.01, the default, noise doesn't count and the darker border and fill do. 4 is more than 3, so the snapshot fails.
    • At color: 0.1, pixelmatch's own default, only the letter counts. The darker border and fill pass unseen.

    visual-check measures colour distance as pixelmatch 8 does, so the cut-offs are approximate. At 0.01, a grey that moves about 2 of 255 doesn't count.

    The measured table behind the defaults

    The defaults come from 606 stories of HeroUI's Storybook, captured in Chromium at scale 1, on amd64 runners and on arm64, with every pixel counted. Each deliberate change was made on arm64 and compared with an amd64 baseline. A row's budget is the largest count that arm64's own differences reached at that color, and a change counts as caught when it went over the budget.

    • color: 0.01 with 19 pixels absorbs every difference between arm64 and amd64. It still catches every 1 px shift, 99% of changed characters and hidden icons, and 89% of background changes of 4 levels. The default budget is 20.
    • At 0.02, arm64 needs no budget at all, but a background 4 levels darker goes unseen: 3 caught of 517.

    The changes: the story's root moved 1 px to the right; the first visible lowercase letter changed; the smallest visible icon of 8 px or more hidden; the largest background in view 4, 8 or 16 levels darker per channel.

    Why a lower color isn't stricter

    A lower color is stricter about each pixel and looser about the snapshot. Noise starts to count as change, the budget has to grow to absorb it, and a large budget hides real changes.

    The table shows it. At color: 0, arm64's differences reach 18,859 pixels. A budget that size catches 45 of 606 one-pixel shifts and 1 of 533 changed characters.

    The default absorbs arm64's differences from amd64, and a dev server's small drift from a static build, on every platform.

    Why anti-aliased pixels count

    pixelmatch can skip a changed pixel that looks like an anti-aliased edge in either image. visual-check keeps that off: every pixel counts, and v1 has no option for it.

    Text and icons are mostly edges, so skipping edges skips most of what they're made of. Measured on the same amd64 runner captures, at color: 0.01 and pixels: 20:

    Every pixel countsEdges skipped
    Budget that absorbs runner noise2 px0 px
    1 px shift caught606 of 606596 of 606
    One character caught488 of 494476 of 494
    Hidden icon caught259 of 260118 of 260

    Skipping edges is for comparing different renderers. visual-check renders every baseline and snapshot in the same container, which leaves 2 pixels of noise on the default platform, so there's little to absorb. pixelmatch's filter that drops a lone changed pixel stays off too.

    CSS pixels at scale 2

    A count in pixels is in CSS pixels. At device scale factor s, a snapshot may have ⌊pixels × s²⌋ changed image pixels, rounded down.

    Device scale factorImage pixels per CSS pixelpixels: 20 allows
    1120
    1.52.2545
    2, the scale for phone modes480
    39180

    A failure shows image pixels against the scaled budget:

    ✗ web  components-card--default  mobile  differs: 84 differ, 80 allowed (20 at scale 2)

    The budget scales because the defaults were measured at scale 1, and phone modes are recommended at scale 2. At scale 2 a change covers 3 to 4 times as many image pixels, and arm64's differences need 69 pixels where they needed 19. An unscaled 20 would fail arm64. 80 absorbs it, and catches nearly as many changes as 20 does at scale 1.

    Percent strings

    pixels also takes a share of the image, as a string from '0%' to '100%':

    parameters: { ...visualCheck({ tolerance: { pixels: '0.1%' } }) },
    • A share counts against the image's own pixels, rounded down to a whole pixel. A 1280 × 720 capture has 921,600 pixels, so '0.1%' allows 921.
    • A share isn't scaled: it already counts image pixels.
    • On a full-page capture, the share grows with the page.
    • Anything else exits 2, such as 1.5, -1 or '0.1'.

    A level sets a count or a share, never both. A share in a story replaces the count it inherits.

    Where to set it

    tolerance is the same object at every level. The most specific level wins, key by key, so a level can set only color or only pixels.

    LevelWhereCovers
    Configtolerance in visual-check.config.tsEvery story
    Previewparameters in .storybook/preview.tsEvery story of one Storybook
    MetaA stories file's default exportThat file's stories
    StoryThe storyThat story
     
    import { visualCheck } from '../.storybook/visual-check'

export const Heatmap: Story = {
  parameters: {
    ...visualCheck({ tolerance: { pixels: '0.5%' } }),
  },
}
    !
    Raise tolerance last

    A snapshot that differs between runs is a flaky snapshot. A mask or a wait hook fixes it without hiding the changes test is there to catch.

    Size differences

    A snapshot whose width or height differs from its baseline always fails, whatever pixels and the masks say. Render noise moves colours, not layout, so a size change is never noise.

    ✗ web  components-card--default  differs: size changed: 1280×2400 → 1280×2432

    The visual diff is padded to the larger size, anchored at the top left, and the padding counts as changed pixels. Changed pixels are magenta and the padding is cyan, over a faded copy of the baseline.

    All keys

    Only storybooks is required. Open a key for its description, or jump to its section below.

    The config file

    • Name: visual-check.config.ts, at the workspace root. .mts, .js and .mjs work too. JSON and YAML don't.
    • Search: the current folder, then each parent up to the git root. The first config found wins, and --config <path> skips the search.
    • Helper: defineConfig, from @visual-check/cli, gives your editor the config's types. It returns the config unchanged.
    • Checks: an unknown key or a wrong type exits 2 before anything is captured.
    import { defineConfig } from '@visual-check/cli'

export default defineConfig({
  storybooks: {
    web: { dir: 'apps/web', url: 'http://127.0.0.1:6006' },
    ui: {
      dir: 'packages/ui',
      url: { local: 'http://127.0.0.1:2137', ci: 'http://127.0.0.1:6007' },
    },
  },
})
    !
    tsconfig paths don't work in the config

    visual-check loads the config through jiti, on every supported Node, and jiti doesn't read paths from your tsconfig. Import with relative paths or package names.

    Everything outside storybooks applies to the whole project. One Storybook's own tolerance or viewport goes in its preview, through visualCheck(...), and its modes go in .storybook/visual-check.ts. See Modes.

    storybooks

    One entry per Storybook, by name. A name takes lowercase letters, digits and -, and it's what the report and --storybook <name> call that Storybook. Every entry runs unless --storybook narrows the run.

    storybooks.<name>.url

    Type
    string | { local?: string; ci?: string }
    Default
    None, required
    CLI
    --url <url>

    Where the running Storybook is served, as an http: or https: URL. visual-check connects to it and never starts or builds one. Use 127.0.0.1, not localhost.

    storybooks: {
  web: { url: 'http://127.0.0.1:6006' },
},
    !
    No user name or password

    url takes no user name or password, because visual-check sends no login. A URL with one exits 2, and the message never shows the password. A Storybook that asks for a login fails the run too.

    Serve Storybook where visual-check runs instead: storybook dev, or its static build served in the same CI job.

    storybooks.<name>.dir

    Type
    string
    Default
    The config file's folder

    The folder Storybook runs in, relative to the config file's folder. index.json's importPath is relative to it. An absolute path works too.

    web: { dir: 'apps/web', url: 'http://127.0.0.1:6006' },

    storybooks.<name>.configDir

    Type
    string
    Default
    '.storybook', inside dir

    Storybook's config folder, relative to dir. visual-check reads the Storybook's modes from visual-check.ts in it.

    docs: { dir: 'apps/docs', configDir: 'config/storybook', url: 'http://127.0.0.1:6008' },

    storybooks.<name>.baselines

    Type
    string
    Default
    '.visual-check/baselines', inside dir

    The folder that holds the Storybook's baselines, relative to dir. It's the only folder you can move in v1. Two Storybooks whose baselines resolve to one folder exit 2.

    web: { dir: 'apps/web', baselines: 'visual/baselines', url: 'http://127.0.0.1:6006' },

    Capture

    platform

    Type
    'linux/amd64' | 'linux/arm64' | 'host'
    Default
    'linux/amd64'

    Where the browser runs: visual-check's Linux container for either CPU architecture, or the machine itself. 'linux/arm64' differs from amd64 by at most 2 of 255 per channel, which the default tolerance absorbs. 'host' gives no parity across machines. There's no flag for it. See Platforms and Docker.

    platform: 'linux/arm64',

    image

    Type
    string
    Default
    The browser package's image

    The Docker image the browser runs in. A custom image must be built FROM the browser package's image. See Browser.

    image: 'ghcr.io/acme/visual-check-chromium:157.0.0',

    viewport

    Type
    { width?: number; height?: number; deviceScaleFactor?: number; touch?: boolean }
    Default
    { width: 1280, height: 720, deviceScaleFactor: 1 }, touch off

    The default capture's viewport, in CSS pixels, when preview sets none. preview, a meta or a story can override any part of it. touch: true turns on touch and mobile emulation together: no hover, a coarse pointer and overlay scrollbars.

    viewport: { width: 1440, height: 900 },

    maskColor

    Type
    string, as #RGB or #RRGGBB
    Default
    '#FF00FF'

    The colour masks are painted in. Changing it changes every baseline that has a mask.

    maskColor: '#000',

    Timezone, locale and colour scheme

    The browser emulates all three, so every machine renders the same dates, numbers and colour scheme. Each changes pixels, so each is one committed value: it can't differ between your machine and CI, and a mode can't set it in v1.

    timezone

    Type
    string, an IANA name
    Default
    'UTC'

    The timezone every story renders in, whatever the machine's own.

    timezone: 'Europe/Warsaw',

    locale

    Type
    string, a BCP 47 tag
    Default
    'en-US'

    The locale the browser reports, which sets how Intl formats dates and numbers.

    locale: 'en-GB',

    colorScheme

    Type
    'light' | 'dark'
    Default
    'light'

    The colour scheme the browser reports to prefers-color-scheme. A dark theme your stories pick through a global is a mode, not this key.

    colorScheme: 'dark',

    Comparison

    tolerance

    Type
    { color?: number; pixels?: number | `${number}%` }
    Default
    { color: 0.01, pixels: 20 }

    How much a snapshot may differ from its baseline before it fails. preview, a meta or a story can override either part. See color and pixels.

    tolerance: { pixels: 10 },

    retries

    Type
    number
    Default
    1

    How many more times test captures a snapshot that differs before it fails. The first capture that passes makes it pass, as a flaky snapshot. A broken story isn't retried, update doesn't use it, and 0 turns retries off.

    retries: 0,

    Run

    workers

    Type
    'auto' | number | { local?, ci? }
    Default
    'auto'
    CLI
    --workers <n>

    The size of the one worker pool for the whole run. 'auto' is the smaller of the CPU count and the memory in GiB, rounded to the nearest GiB, minus 1, read where the browser runs. That gives 2 on a private repo's hosted runner, 4 on a public repo's, and 7 in Docker Desktop's default VM.

    workers: { local: 'auto', ci: 2 },

    readyTimeout

    Type
    number | { local?, ci? }, in milliseconds
    Default
    10_000

    One limit for everything before the capture, the wait hook and the end state included. Running out makes a broken story, and the message says which step it was in.

    readyTimeout: { ci: 20_000 },

    silenceHosts

    Type
    string[]
    Default
    []

    Exact hosts, or *.example.com patterns. update's two end-of-run warnings, about real network requests and about remote content, stay silent for these hosts.

    silenceHosts: ['images.example.com', '*.cdn.example.com'],

    affected.selectAll

    Type
    string[], globs
    Default
    []

    Globs relative to the config file's folder. A changed file that matches selects every story. * and ** skip names that start with ., so name the dot, as in **/.env*.

    affected: { selectAll: ['packages/tokens/**', '**/.env*'] },

    affected.ignore

    Type
    string[], globs
    Default
    []

    Globs relative to the config file's folder. A changed file that matches selects nothing, whatever else it is.

    affected: { ignore: ['**/*.md', 'docs/**'] },

    Local runs and CI

    Three keys take a { local, ci } pair: storybooks.<name>.url, workers and readyTimeout. They set how visual-check reaches Storybook and how fast it runs. Nothing that changes pixels can differ between your machine and CI, and the type rejects a pair on any other key.

    export default defineConfig({
  storybooks: {
    web: { url: { local: 'http://127.0.0.1:6006', ci: 'http://127.0.0.1:8080' } },
  },
  workers: { ci: 2 },
  readyTimeout: { ci: 20_000 },
})
    • The CI environment variable picks the side.
    • A missing side takes the key's default, except for url, which has none: a run on that side exits 2.
    • There are no local or ci blocks.

    init under Rush

    init reads the package manager from rush.json. Rush owns installs, so init prints the install steps instead of running them:

    Install visual-check's packages yourself, then add the addon:
  cd . && rush add --dev --exact --skip-update -p @visual-check/cli@0.1.0
  rush update
  cd libs/ui && pnpm exec storybook add @visual-check/storybook-addon@0.1.0 --yes --skip-install
    • The workspace root needs a package.json, for the root's scripts and the CLI. Without one, init stops and writes nothing.
    • A package only Rush lists gets no scripts of its own, since its scripts can't find the root's CLI. Run visual-check test --storybook <name> from the root instead.
