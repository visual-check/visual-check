    Getting started

    Set up visual-check, write the first baselines and check your stories against them.

    i
    Readiness never waits for the network

    visual-check captures a story once it has finished and its images and fonts have loaded. It doesn't wait for network requests. So when the first test fails, a story usually needs tuning: a wait hook for late content, a mask for content that changes, or a look at its animations. What to tune.

    What you need

    • Node 22.17 or later.
    • Storybook 9.1, 10 or 11. The Storybook addon needs Storybook 10.
    • Docker, running. The browser runs in a container, so every machine captures the same pixels.
    • npm, pnpm, Yarn 1, Yarn 4.17.1 or later, or Bun.

    Set up

    Run init

    Run it anywhere in the repo: inside a package, it works at the workspace root and says so. It installs visual-check's packages itself, so there's no separate install step.

    $

    init finds every Storybook through its .storybook/main.* file, works out the command and port that start it, and checks Docker. Then it asks its questions. Arrows choose, and an answered question collapses to one line.

    QuestionIts hint in the terminal
    Package managerOnly when nothing names oneNo lockfile or packageManager field names one.
    Storybooks to set upOnly when there are severalThe ones ticked go in the config.
    Name of the Storybook in apps/webWhat the config and the report call this Storybook.
    URL of webWhere visual-check opens it, locally and in CI. Use 127.0.0.1, not localhost.
    Command that starts webOnly when no script starts itNo script starts this Storybook. The next steps show this command.
    Name of the script that runs visual-check testCompares each story with its baseline. Default visual:check.
    Name of the script that runs visual-check updateWrites the baselines. Default visual:update.
    Install the agent skill?Teaches a coding agent to run visual-check and report what changed. Default yes.
    Add the Storybook addon to web?Storybook 10 onlyCheck and update the open story from inside Storybook. Default yes.

    It never asks about the platform, tolerance or workers, and one URL serves both local runs and CI. init --yes takes every default.

    !
    Yarn 4 on a release day

    Yarn 4 refuses a package published less than a day ago, so yarn dlx @visual-check/cli init can fail on the day of a release. Wait a day, or list @visual-check/* under npmPreapprovedPackages in .yarnrc.yml.

    It adds @visual-check/cli and @visual-check/chromium, the browser, at the workspace root, and @visual-check/storybook and the addon in the Storybook's package. It never edits preview.*, your other scripts or the root .gitignore, touches main.* only through storybook add, and writes no CI workflow.

    visual-check.config.ts
    import { defineConfig } from '@visual-check/cli'

export default defineConfig({
  storybooks: {
    web: { url: 'http://127.0.0.1:6006' },
  },
})

    The config names each Storybook and where it runs, and holds only what differs from the defaults. Options for stories live in Storybook parameters, written with the helper init puts next to your preview:

    .storybook/visual-check.ts

// To set options for every story, spread visualCheck into the parameters in your preview file:
//   import { visualCheck } from './visual-check'
//   parameters: { ...visualCheck({}) },
export const visualCheck = defineVisualCheck({
  modes: {
    // Each mode a story lists adds one snapshot besides its default capture. For example:
    // mobile: { viewport: { width: 375, height: 667, deviceScaleFactor: 2, touch: true } },
  },
})

    It ends by printing the next steps:

    Terminal

    Start Storybook

    visual-check never starts or builds a Storybook. It connects to the one running at the URL in the config, so start yours in its own terminal and keep it running.

    $

    Write the first baselines

    update captures every story and writes a baseline for each one that has none. It writes a baseline only when two loads of the story agree, so a baseline is never a one-off frame.

    Terminal

    update runs on your machine only. With CI set it exits 2, and no CI job ever writes a baseline.

    Check the stories

    test captures each story again and compares the snapshot with its baseline. Straight after update, every story passes:

    Terminal
    $ 
visual-check 0.1.0 · test · 108 snapshots · 4 workers
108 passed · 10.8s
Report: .visual-check/report/report.json

    In a terminal, passing stories print nothing while the run goes. Only failures print a line, and the run ends with the counts. It exits 0 when every story passes.

    Commit the baselines

    Baselines are PNG files in .visual-check/baselines/, next to the Storybook. Commit them with the rest of the setup, so CI and the rest of your team compare against the same images. The .gitignore that init wrote keeps the report out of git.

    To run visual-check on every pull request, see CI.

    Each failure names its visual diff: one image, magenta where pixels differ, over a faded copy of the baseline. The Storybook addon shows the same images, with the same wipe, inside Storybook.

    1904 pixels differ. The mobile mode captures at scale 2, where the default budget of 20 CSS pixels allows 80 image pixels, so the snapshot fails and test exits 1.

    If the change is intended, run update and commit the new baselines with the code that changed them. If it isn't, fix the code. Don't raise the tolerance to make a real change pass: color and pixels explains what it absorbs.

    If the first test fails

    A story can pass in Storybook and still fail its first test. These are the usual causes, each with its fix:

    • Late content, such as data from an API or icons loaded by script: a wait hook that waits for it.
    • Content that changes every run, such as a clock or a random avatar: a mask.
    • Images from another origin: a CDN can serve different bytes to different machines. See Remote content.
    • Motion visual-check can't reach, such as a canvas or a Lottie file: a mask or a wait hook. See Animations.

    Options go in the story's parameters, through the helper init wrote:

    Dashboard.stories.tsx
    import { visualCheck } from '../.storybook/visual-check'

export const Default: Story = {
  parameters: {
    ...visualCheck({
      masks: { clock: { selector: '[data-clock]' } },
      wait: async ({ canvas }) => {
        await canvas.findByText('Revenue this month')
      },
    }),
  },
}

    A snapshot that fails and then passes on its retry is a flaky snapshot. It doesn't fail the run, and it's listed by name at the end, so you can fix it later.

    color and pixels

    A snapshot passes when it differs from its baseline by no more than the story's tolerance. Tolerance asks two questions: did this pixel change, and how many changed pixels are allowed?

    Two questions, two keys

    color decides whether one pixel counts as differing. It's a number from 0 to 1: how far a pixel's colour may move and still count as unchanged. At the default, 0.01, a grey shift of up to about 2 of 255 doesn't count.

    pixels decides how many differing pixels a snapshot may have and still pass. The default is 20.

    visual-check.config.ts
    export default defineConfig({
  storybooks: { web: { url: 'http://127.0.0.1:6006' } },
  // The defaults, written out
  tolerance: { color: 0.01, pixels: 20 },
})

    Ten pixels, worked through

    The figure holds ten pixels from the edge of a button's label, as the baseline and the snapshot show them. Under each pair is how far its colour moved, on the same 0 to 1 scale as color. Pixels that count as differing light up magenta in the visual diff.

    It starts at color: 0.01 with a budget of 2. Pixels 2 and 7 moved by raster noise, 1 and 2 of 255, and don't count. The anti-aliased edges of the stroke moved further, so pixels 3 and 6 count. Pixels 9 and 10 are a deliberate change: a new stroke. Four pixels differ and two are allowed, so the snapshot fails.

    Try these:

    1. Turn the deliberate change off. Only the anti-aliased edges are left: 2 differ, 2 allowed, and the snapshot passes. That's the budget's job: absorbing the few edge pixels that move between machines.
    2. Set color to 0. Noise counts too now. Four pixels differ on a snapshot with no deliberate change, so the budget would have to grow to 4 just to pass it.
    3. Turn the change on and set color to 0.05. The edges stop counting, the count drops to 2, and the snapshot passes with the change in it.
    4. Switch to scale 2. Every CSS pixel is now 2 × 2 image pixels, so four times as many pixels differ, and the budget grows by the same factor. The result doesn't change.

    A real snapshot has far more pixels: the default budget of 20 is against 921,600 at 1280 × 720. The strip scales that down to ten.

    Why a lower color isn't stricter

    Lowering color makes more pixels count, and most of the new ones are noise. The budget then has to grow to absorb it, and a bigger budget lets real changes through.

    In the measurements behind the defaults, at color: 0 the noise between arm64 and amd64 needs a budget of 18,859 pixels, and that budget misses 561 of 606 one-pixel shifts. The table has every row.

    Anti-aliased pixels count

    Anti-aliased pixels, the soft edges of text, icons and shapes, count like any other pixel. There's no option to ignore them in v1, and pixelmatch's filter that drops a lone differing pixel stays off.

    A small icon is mostly edge. In the measurements behind the defaults, the default budget caught 118 of 260 hidden icons with anti-aliased pixels ignored, and 259 with every pixel counted.

    CSS pixels and scale

    A count in pixels is in CSS pixels. At a device scale factor of s, a snapshot may have ⌊pixels × s²⌋ differing image pixels.

    Where the defaults come from

    The defaults were measured on 606 stories of a public component library's Storybook, at 1280 × 720 and scale 1. For each color, the budget is the most pixels that platform noise produced between arm64 and amd64. Each deliberate change was made on arm64 and compared with an amd64 baseline. The table counts the changes caught, out of the stories where the change was visible.

    At 0.01, a budget of 20 lets every difference between arm64 and amd64 pass, and still catches 89–100% of the small deliberate changes. pixelmatch's own default, 0.1, catches no background change of up to 16 levels: it measures perceived colour, and a uniform shift that size is below it.

    Percent strings

    pixels also takes a share of the image, as a string from '0%' to '100%'. A share is counted against the image's own pixels, so it isn't scaled, and it's rounded down to a whole pixel.

    ValueMeans
    A whole number, 0 or more, such as 20A count of differing CSS pixels
    A string from '0%' to '100%', such as '0.1%'A share of the image's own pixels
    Anything else, such as 1.5, -1 or '0.1'Exit 2

    On a 1280 × 720 snapshot, '0.1%' allows 921 differing pixels. On a full-page snapshot twice as tall, it allows twice as many. A level sets a count or a share, never both, and each level replaces the budget it inherits.

    Setting tolerance

    Set it in the config for every Storybook, in preview for one Storybook, in a meta for one stories file, or on a story. It deep-merges, so a level can set only color or only pixels.

    Chart.stories.tsx
    import { visualCheck } from '../.storybook/visual-check'

export const Default: Story = {
  parameters: {
    ...visualCheck({ tolerance: { pixels: '0.1%' } }),
  },
}

    Retries and update's stability checks use each story's own tolerance.

    !
    A size change always fails

    A snapshot whose width or height differs from its baseline fails whatever pixels and the masks say. The report shows both sizes, such as 1280×2400 → 1280×2432, and the visual diff marks the padding in cyan.

    Animations

    A snapshot shows how a story ends, not a moment in the middle. visual-check lets your animations run, then brings the page to its end state just before it captures.

    What a snapshot shows

    Every snapshot shows the end state:

    • finite animations and transitions, CSS or script, as if they had finished;
    • infinite animations on their first frame;
    • videos, animated GIFs and SVG animation on their first frame.

    The figure shows three stories as they run in Storybook and as they're captured. The spinner's animation is infinite, so it's captured on its first frame. The toast fades in once, so it's captured fully in. The progress bar's transition ends at 70%, so it's captured there.

    The end state is always on, and there's no option. A story with nothing running pays nothing for it.

    How the page gets there

    After the story has finished and any wait hook has run, visual-check:

    1. finishes every running finite animation: in the document, in every shadow root and in every same-origin frame;
    2. lets a frame pass, so end events run your page's logic, such as removing a toast's entering class;
    3. repeats both until two checks a frame apart find nothing finite running, for at most 20 rounds;
    4. puts whatever still runs on its first keyframe: infinite animations, and any that can't finish;
    5. freezes media: videos go back to their first frame, inline SVG animation pauses at 0, and an animated GIF in an <img> shows its first frame;
    6. checks images and fonts again if anything changed, then captures.

    Animations your page paused itself, and scroll-driven ones, are left alone.

    i
    It counts toward readyTimeout

    readyTimeout, 10 seconds by default, covers everything up to the capture, this step included. Running out makes a broken story, and its message names the step it was in.

    play runs as in Storybook

    visual-check waits for Storybook's storyFinished event, which comes after play and afterEach. Until then the story runs as it does in plain Storybook: play sees real durations and every end event, so a step that awaits an animation works the same.

    The end state comes only after that, at capture. An end screen worth a baseline is written as a story with play.

    Reduced motion

    The capture reports no preference for reduced motion: to the page, prefers-reduced-motion matches no-preference. Stories render the motion most people see, and the snapshot shows where it ends. visual-check adds no stylesheet that turns animations off.

    What's left to you

    Some motion is out of visual-check's reach. Each of these shows whatever frame it's on at capture, so it can differ from run to run:

    • SVG in an <img>, and CSS animations inside an SVG image;
    • SVG animation used as a CSS image behind a URL that doesn't end in .svg, or cross-origin without CORS;
    • GIFs as CSS backgrounds, at a URL without .gif, or picked by a <source> in <picture>;
    • a video that hasn't loaded anything;
    • APNG, animated WebP, canvas, Lottie and other script-driven motion;
    • animations and media inside cross-origin frames.

    Mask what can't be stopped, or wait in a wait hook for it to reach a stable state. The hook runs before the end state:

    Upload.stories.tsx
    import { visualCheck } from '../.storybook/visual-check'

export const Uploading: Story = {
  parameters: {
    ...visualCheck({
      masks: { lottie: { selector: '[data-lottie]' } },
    }),
  },
}

export const Done: Story = {
  parameters: {
    ...visualCheck({
      // The canvas chart sets its label once it has drawn
      wait: async ({ canvas }) => {
        await canvas.findByRole('img', { name: 'Uploads by day' })
      },
    }),
  },
}

    A mask paints an opaque box in maskColor over the element's box, in the baseline and the snapshot alike. If the element grows or moves, its box does too, and those pixels count.

    A story fails with "84 differ, 80 allowed (20 at scale 2)". Why 80, when pixels is 20?

    From 2 pages

    pixels counts CSS pixels. The story's mode captures at scale 2, where one CSS pixel is 2 × 2 image pixels, so a count of 20 allows ⌊20 × 2²⌋ = 80 image pixels. The snapshot has 84, so it fails.

    • Open the visual diff the failure names and look at what changed.
    • If the change is intended, run visual-check update and commit the new baseline.
    • If it isn't, fix the code. Raising pixels hides real changes too: at scale 2, a one-character change covers a median of 199 image pixels, so pixels: 50 would let about half of them through.
