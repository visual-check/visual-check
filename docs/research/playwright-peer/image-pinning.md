# Browser / Playwright image pinning: facts

Researched 2026-11-11. Registry data comes from anonymous MCR v2 API calls (manifests, config blobs and referrers only, no layer blobs). "Unknown" means no primary source found.

## 1. Playwright Docker image (`mcr.microsoft.com/playwright`)

### Publishing pipeline

| Fact | Source |
|---|---|
| Since 2026-07 the images are built and pushed by an Azure DevOps pipeline. It runs on any `v*` git tag except prereleases (`exclude: v*-*`) and can also be queued by hand (`releaseChannel` stable/canary). No GitHub workflow publishes Docker images any more. | [.azure-pipelines/publish-docker.yml](https://github.com/microsoft/playwright/blob/main/.azure-pipelines/publish-docker.yml), commit [615e1c7](https://github.com/microsoft/playwright/commit/615e1c7844) "move docker publishing to AzDO" |
| Stable tags pushed per release: `v<ver>-jammy`, `v<ver>-noble`, `v<ver>` (an alias of noble), and `v<ver>-resolute`. Each is also pushed as `-amd64` and `-arm64` tags, then joined into a multi-arch manifest. Manual canary runs push `v<ver>-canary-<timestamp>-*`. | [utils/docker/publish_docker.sh](https://github.com/microsoft/playwright/blob/main/utils/docker/publish_docker.sh) |
| Every pushed tag gets an OCI referrer of type `application/vnd.microsoft.artifact.lifecycle`, with annotation `vnd.microsoft.artifact.lifecycle.end-of-life.date=<push day>`. In effect each image is marked end-of-life on the day it ships. | same script (`attach_eol_manifest`), added in [PR #29847](https://github.com/microsoft/playwright/pull/29847) (2024-03), whose stated reason links to an internal Microsoft page |
| Verified on the registry: the amd64 manifest of `v1.65.0-noble` has 2 lifecycle referrers dated `2026-11-05`, the release day. `v1.64.0-noble` has EOL `2026-10-08` and `v1.62.0-noble` has EOL `2026-07-27`. | `GET https://mcr.microsoft.com/v2/playwright/referrers/sha256:bc4fbb32…` |
| The Dockerfile does not pin its inputs. It uses `FROM ubuntu:noble`, the latest NodeSource `node_${NODE_VERSION}.x` (currently `26`), unpinned `apt-get`, and `playwright-core install-deps`, which installs system and font packages. Browsers are installed by the bundled `playwright-core`, so the browser revision is fixed by the Playwright version. A rebuild of the same tag can therefore change OS libraries, fonts and Node, but not the browser build. | [utils/docker/Dockerfile.noble](https://github.com/microsoft/playwright/blob/main/utils/docker/Dockerfile.noble) |

### Are existing tags rebuilt or republished?

| Evidence | Source |
|---|---|
| **Stated policy: no.** A maintainer wrote "We don't publish docker images between releases. If you need the latest fixes, you should build it using the docker file…" (2026-06-03). Others said "We publish Docker images upon release… If you need your scans resolved faster, build the image yourself" (2026-07-08) and "It'll be picked up by the release process when we release" (2026-03-30). | [#41120](https://github.com/microsoft/playwright/issues/41120), [#41694](https://github.com/microsoft/playwright/issues/41694), [#39511](https://github.com/microsoft/playwright/issues/39511) |
| **Usual practice matches the policy.** For 1.40.0, 1.45.0, 1.48.0, 1.50.0, 1.52.0, 1.55.0, 1.58.0, 1.60.0 and 1.63.0, the amd64 config `created` time falls within about 1 hour of the GitHub release. `v1.61.1-noble` still has the digest `sha256:5b8f294a…` that a user quoted on 2026-07-08. | config blobs on MCR; [GitHub releases](https://github.com/microsoft/playwright/releases); [#41694](https://github.com/microsoft/playwright/issues/41694) |
| **Counterexample: `v1.64.1-*` was rebuilt in place at least twice.** The first build was on 2026-10-14. Users reported a rebuild on 2026-10-23 that fixed a Node CVE, and a maintainer closed the issue. The amd64 image now on the tag was created `2026-11-01T17:56Z`, with EOL referrer `2026-11-01`. A later report says the 11-01 rebuild also picked up a patched Ubuntu `libbrotli1`. That report was against the Python image, and the maintainer answered "Docker for 1.65 is live" rather than rebuilding it. | [#43581](https://github.com/microsoft/playwright/issues/43581), [playwright-python#3315](https://github.com/microsoft/playwright-python/issues/3315), MCR config `sha256:a0d7b2b4…` |
| `v1.62.0-noble` was created 2026-07-27, three days after the 2026-07-24 release. The reason is unknown: it could be a delayed first publish or a rebuild. | MCR config; release page |
| Whether earlier digests of a rebuilt tag (such as the 2026-10-14 `v1.64.1` build) can still be fetched by digest: **unknown**. | — |
| Their security stance: the image is "intended to be used for testing and development purposes only". | [docs/src/docker.md](https://github.com/microsoft/playwright/blob/main/docs/src/docker.md), [#22979](https://github.com/microsoft/playwright/issues/22979) |

### Tags, digests, size

| Fact | Source |
|---|---|
| The registry holds 18,636 tags, mostly legacy `sha-*`. No minor-version tags exist (no `v1.65-noble` or `v1.65` style). | [tags/list](https://mcr.microsoft.com/v2/playwright/tags/list) |
| Moving tags `latest`, `noble`, `jammy`, `focal`, `next`, `next-noble` and others still exist but are **frozen at v1.46.1 (2024-08-16)**. `noble` has the same digest as `v1.46.1-noble` (`sha256:c9e3fddb…`), and `latest` the same as `v1.46.1-jammy` (`sha256:02810c97…`). They were dropped from the publish script in commit [cae779b](https://github.com/microsoft/playwright/commit/cae779b74f) ([PR #31435](https://github.com/microsoft/playwright/pull/31435)), and the docs no longer list them. | manifests API; script history |
| `v1.65.0-noble` is an OCI image index with digest `sha256:6e3fb709361521eb27161606e6da6d2674e5e89fa16516cb37d6fdd91372273d`, the same as `v1.65.0`. Its linux/amd64 manifest is `sha256:bc4fbb329a25287ed23e9216c97063646abdd1bf2da669a9895fa3e2078b2302`, made of 7 layers. **Compressed size: 1,002,814,156 B (≈1.00 GB / 956 MiB).** Its config is labelled `org.opencontainers.image.version=1.65.0`. | `manifests/v1.65.0-noble`, `manifests/sha256:bc4f…` |
| `v1.64.1-noble`: index `sha256:2f05f8a7…`, amd64 990,220,611 B (≈990 MB) as of the 2026-11-01 build. | manifests API |
| Docs list only the `v<ver>`, `-noble`, `-jammy` and `-resolute` tags, and say "It is recommended to always pin your Docker image to a specific version… If the Playwright version in your Docker image does not match the version in your project/tests, Playwright will be unable to locate browser executables." For remote `run-server` they say to "ensure the Playwright version in your tests matches the version running in the Docker container." **The docs say nothing about digests.** | [docs/src/docker.md](https://github.com/microsoft/playwright/blob/main/docs/src/docker.md) ("Image tags", "Remote connection") |

### Browser per Playwright version

| Fact | Source |
|---|---|
| "Each version of Playwright needs specific versions of browser binaries… With every release, Playwright updates the versions of the browsers." | [browsers.md](https://playwright.dev/docs/browsers) |
| Chromium changes only on minor releases in every case sampled. 1.64.0 and 1.64.1 both ship r1248 (156.0.8078.4), and 1.65.0 ships r1254 (158.0.8127.18). Chromium, Firefox and WebKit are identical across 1.58.0/1/2, 1.59.0/1, 1.61.0/1 and 1.62.0/1. | `packages/playwright-core/browsers.json` at each tag ([e.g. v1.65.0](https://github.com/microsoft/playwright/blob/v1.65.0/packages/playwright-core/browsers.json)) |

## 2. `repo:tag@sha256:<index digest>` with `--platform`

| Fact | Source |
|---|---|
| The reference grammar allows both parts: `reference := name [ ":" tag ] [ "@" digest ]`. | [distribution/reference reference.go](https://github.com/distribution/reference/blob/main/reference.go) |
| `ParseDockerRef` follows "the docker convention, which allows for references to contain both a tag and a digest… For references containing both a tag and a digest, it returns a digested reference". The tag is dropped, so only the digest is used. | [normalize.go](https://github.com/distribution/reference/blob/main/normalize.go) |
| Docker's own example is `FROM alpine:3.21@sha256:…`: "even if a publisher replaces the tag with a new image… your builds would still use the pinned image version". The trade-off is that you are "opting out of automated security fixes". Dependabot and Docker Scout can update these pins. | [Docker build best practices, "Pin base image versions"](https://docs.docker.com/build/building/best-practices/#pin-base-image-versions) |
| "A digest takes the place of the tag when pulling an image… Docker does therefore not pull updated versions of an image". `--platform` is described as "Set platform if server is multi-platform capable". | [docker image pull](https://docs.docker.com/reference/cli/docker/image/pull/) |
| `FROM [--platform=<platform>] <image>[@<digest>]`: "The optional `--platform` flag can be used to specify the platform of the image in case `FROM` references a multi-platform image." | [Dockerfile reference, FROM](https://docs.docker.com/reference/dockerfile/#from) |
| An index digest identifies the index itself. Its `manifests[]` entries carry a `platform`, and "If multiple manifests match a client or runtime's requirements, the first matching entry SHOULD be used." Docker "automatically selects the correct variant" from a manifest list. | [OCI image-index spec](https://github.com/opencontainers/image-spec/blob/main/image-index.md), [Docker multi-platform](https://docs.docker.com/build/building/multi-platform/) |
| **Conclusion (inference from the above):** `mcr.microsoft.com/playwright:v1.65.0-noble@sha256:6e3fb709…` with `--platform linux/amd64` resolves the index and then the amd64 entry (`sha256:bc4fbb32…`). No docs.docker.com page shows `docker run --platform` with an index digest explicitly. Alternative: pin the amd64 manifest digest directly; it is single-platform, so `--platform` then only asserts the platform. | — |

### Pattern

- **Pin per own release:** Puppeteer (with semver rules for browser rolls), Lost Pixel (image and exact `playwright-core`), BackstopJS (image tag = package version), Loki (default image), Cypress Electron, and Cypress full-version image tags.
- **Follow the user's install:** Playwright Test, Storybook test-runner, Vitest, Argos, reg-suit/storycap.
- **Vendor-managed cloud:** Chromatic (windowed opt-in, then forced upgrade with auto-accepted baselines), Percy, Happo.
